# OpenCode v2.0.0 Implementation Plan

## Status

This document is the implementation plan for the next major release,
`opencode-models-discovery@2.0.0`.

The release will make OpenCode v2 the primary and stable integration. The
existing OpenCode v1 adapter will remain available as legacy support so that
existing users can upgrade without an immediate configuration migration.

This is an implementation and release document, not a promise that every
OpenCode v1 behavior will gain a V2 equivalent.

## Release policy

### OpenCode v2: stable and primary

OpenCode v2 is the main development and test target for `2.0.0` and later
minor releases. New user-facing functionality should target the V2 provider
lifecycle, host storage, Integration credentials, TUI, RPC, and Agent Tools.

The stable V2 contract includes:

- top-level `plugins` and `providers` configuration;
- provider-scoped discovery under `providers.<id>.settings.modelsDiscovery`;
- generic OpenAI-compatible model discovery;
- provider reload and in-memory inventory management;
- `/connect` Integration-backed credentials;
- credential lifecycle reactivity;
- host-managed, credential-free discovery caching;
- `/models-discovery-refresh`;
- `/models-discovery-console`;
- `models_discovery_refresh`; and
- `models_discovery_status`.

### OpenCode v1: legacy compatibility

The V1 adapter remains supported for compatibility, security fixes, and severe
regressions. Existing V1 configuration and behavior should continue to work,
but V1 is no longer the primary feature-development target.

Legacy support includes, unless a future major release explicitly changes the
policy:

- the V1 `plugin` / `provider` configuration shape;
- provider-level V1 discovery settings;
- the V1 config and event hooks;
- the V1 XDG discovery cache format;
- V1 auth-store fallback behavior;
- `/models-discovery:config`;
- `/models-discovery:migrate`; and
- existing Mimocode compatibility where it remains supported by the host.

V1 does not automatically gain new V2-only features such as host-managed
storage semantics, V2 RPC operations, or V2 provider lifecycle behavior.

The package will continue to ship one combined entrypoint:

```text
OpenCode v1 -> default.server(input, options)
OpenCode v2 -> default.id + default.setup(ctx)
```

The adapter boundaries remain:

```text
src/core/       Host-independent discovery, filtering, enrichment, and mapping
src/v2/         OpenCode v2 stable adapter
src/plugin/     OpenCode v1 legacy adapter
src/runtime.ts  Combined package entrypoint
```

### Support matrix

| Capability | OpenCode v2 | OpenCode v1 |
|---|---|---|
| Host integration | Stable / primary | Legacy |
| Configuration | `plugins` / `providers` | `plugin` / `provider` |
| Discovery settings | `providers.<id>.settings.modelsDiscovery` | `provider.<id>.options.modelsDiscovery` |
| Provider lifecycle | Host provider transforms and reload | V1 config/event hooks |
| Credentials | `ctx.integration` and `/connect` | Resolved provider key and XDG auth fallback |
| Discovery cache | Host `ctx.storage` | V1 XDG provider state |
| Override storage | `overrides:<providerID>:<modelID>` | Existing V1 provider model state |
| TUI / RPC | V2 console, refresh, status, cache, overrides | V1 helper commands |
| New feature development | Supported | Security and severe regression fixes |

V1 legacy maintenance for the `2.x` line includes compatibility, security
fixes, and severe regressions. New V2 lifecycle, storage, RPC, TUI, and model
override features are not backported to the V1 adapter unless a compatibility
fix is required to preserve existing V1 behavior.

### Validated host versions

The release keeps combined host compatibility:

- OpenCode v1 minimum: `1.18.29`;
- OpenCode v2 minimum validated version: `2.0.26`;
- `@opencode/plugin`: pinned to `2.0.26`;
- package `engines.opencode`: `>=1.18.29`.

The engines range remains combined so V1 users do not receive an unnecessary
package compatibility warning. V2 validation and release testing use
OpenCode/`@opencode/plugin` `2.0.26` as the minimum supported V2 baseline.

## Goals

`2.0.0` is complete when the following are true:

1. OpenCode v2 is documented and tested as stable rather than beta.
2. A configured generic OpenAI-compatible provider can discover, refresh, and
   execute discovered models through the V2 runtime.
3. V2 credentials can be supplied through `/connect` without writing secrets
   to configuration, cache, diagnostics, or logs.
4. V2 cache behavior is deterministic across refresh, expiry, restart, clear,
   and corruption scenarios.
5. V2 TUI and Agent Tool operations have stable contracts and useful failure
   behavior.
6. V1 remains usable as a clearly documented legacy adapter.
7. The published npm package loads correctly in both supported host
   generations and from compiled distribution artifacts.

## Scope and decisions required

### Model-level overrides

The current V2 RPC registration contains placeholder implementations:

```ts
overrideList -> { overrides: [] }
overrideSet  -> { success: true }
overrideDelete -> { success: true }
```

These must not remain as silent false-success operations in the stable V2
contract.

Before implementation is considered complete, choose one of the following:

#### Preferred: implement V2 overrides

Implement provider/model-scoped overrides using the V2 host storage boundary.
The implementation must define:

- a versioned storage schema;
- provider ID and model ID identity;
- list, set, and delete operations;
- validation and rejection of credential or authorization fields;
- application of overrides after discovery and before the V2 projection;
- behavior when a model temporarily disappears from discovery;
- precedence relative to discovered metadata and explicit provider config;
- provider-scoped and all-provider cache clearing interaction; and
- tests for persistence, corruption, and redaction.

#### Alternative: remove V2 override operations

If overrides are not part of `2.0.0`, remove them from the V2 public RPC
definition and documentation. Do not retain operations that report success
without changing state. A future version can add them as a new capability.

The release cannot be marked stable while these operations have misleading
placeholder behavior.

### Configuration contract

The following V2 configuration path is the stable path:

```text
providers.<provider-id>.settings.modelsDiscovery
```

The implementation must document and test:

- explicit `enabled` behavior;
- default discovery endpoint and origin-relative endpoint resolution;
- timeout defaults and validation;
- filtering and enrichment options;
- cache defaults and TTL behavior;
- `integrationID` resolution;
- explicit model precedence;
- provider package and base URL handling; and
- the fact that V1 configuration paths are not read by the V2 adapter.

V2 must not silently read `plugins[].options.providers` or V1
`provider.<id>.options.modelsDiscovery` as an alternative configuration
source.

## Implementation workstreams

### 1. V2 provider lifecycle

- [ ] Verify initial provider discovery from `ctx.provider.list()`.
- [ ] Verify providers with no seed models.
- [ ] Verify provider add, update, and removal after `config.updated`.
- [ ] Verify package, name, base URL, endpoint, and discovery settings changes.
- [ ] Verify inventory replacement does not retain removed models.
- [ ] Verify provider transforms remain replay-safe and side-effect free.
- [ ] Verify reloads do not create refresh loops.
- [ ] Verify refresh requests are serialized and force-refresh intent is not
      lost while another refresh is active.
- [ ] Preserve explicit provider/model configuration according to the defined
      precedence rules.

### 2. Discovery and model projection

- [ ] Verify generic OpenAI-compatible `/v1/models` discovery.
- [ ] Verify custom `/models` and other configured endpoint paths.
- [ ] Verify request timeout, HTTP failure, malformed response, and empty
      response behavior.
- [ ] Verify filters, classification, enrichment, naming, and reasoning
      variants against the shared core.
- [ ] Add field-level V2 contract tests for `modelID`, limits, capabilities,
      modalities, attachments, reasoning, variants, and cost metadata.
- [ ] Verify discovered models become visible through the host model API.
- [ ] Verify a selected discovered model reaches the configured runtime
      endpoint with the expected API model ID.

### 3. Credentials and security

- [ ] Verify explicit `settings.apiKey` credentials.
- [ ] Verify host-resolved environment substitutions.
- [ ] Verify native `/connect` Integration credentials.
- [ ] Verify credential updates, switching, revocation, and re-resolution.
- [ ] Verify discovery and runtime requests use the current credential.
- [ ] Verify credentials never appear in `opencode.json`, V2 storage, status
      output, RPC output, diagnostics, or logs.
- [ ] Verify stale authorization headers are removed after credential
      revocation or switching to an unauthenticated provider.
- [ ] Verify custom provider names and IDs do not collide with built-in
      provider names in Integration registration.

### 4. V2 cache

- [ ] Keep caching disabled by default.
- [ ] Verify enabled caches use only the host-provided `ctx.storage` API.
- [ ] Verify cache identity includes the provider identity and discovery
      inputs needed to prevent incorrect cache hits.
- [ ] Verify fresh cache hits avoid unnecessary provider requests while still
      rebuilding the current V2 projection.
- [ ] Verify expired entries trigger live discovery.
- [ ] Verify force refresh bypasses fresh entries.
- [ ] Verify service restart restores inventory from valid host-managed cache.
- [ ] Verify corrupt, unsupported, and identity-mismatched entries are safe
      cache misses.
- [ ] Verify Provider cache clear and clear-all operations affect only the
      plugin's V2 cache namespace.
- [ ] Verify raw-cache inspection remains credential-free.
- [ ] Keep V1 XDG cache files separate and do not import them into V2.

### 5. TUI, RPC, and Agent Tools

- [ ] Stabilize `/models-discovery-refresh` behavior and error messages.
- [ ] Stabilize `/models-discovery-console` Provider -> Model -> Details
      navigation.
- [ ] Verify Provider filtering.
- [ ] Verify model details include the supported structured metadata.
- [ ] Verify cache inspection, force refresh, Provider clear, and clear-all
      actions.
- [ ] Verify no-provider, empty-provider, failed-provider, and unavailable-RPC
      states.
- [ ] Verify `models_discovery_refresh` input/output schema.
- [ ] Verify `models_discovery_status` input/output schema, including
      `providerID` and `rawCache` behavior.
- [ ] Ensure all user-visible errors are actionable and credential-free.

### 6. V1 legacy isolation

## Test strategy

The existing unit tests remain necessary but are not sufficient for `2.0.0`.
The release must add or enable the following layers.

### Shared-core tests

Continue testing filtering, naming, mapping, enrichment, endpoint handling,
and cache identity independently of either host generation.

### V1 contract tests

Keep the existing V1 test suite passing, including:

- config hook behavior;
- event hook behavior;
- legacy config warnings and migration commands;
- XDG cache behavior;
- auth-store fallback;
- explicit model merging; and
- Mimocode compatibility where applicable.

### V2 contract tests

Cover the V2 plugin Context with focused tests for:

- provider and Integration transform registration;
- provider reload behavior;
- provider lifecycle events;
- discovery and inventory replacement;
- credential lifecycle;
- host storage cache;
- RPC registration and schema behavior;
- TUI command behavior; and
- Agent Tools.

### OpenCode v2 integration tests

Run a real or pinned OpenCode v2 service against a local mock
OpenAI-compatible server and verify:

1. The plugin loads from the published-style compiled directory.
2. A provider with no seed models is registered.
3. `/v1/models` discovery populates the provider.
4. The discovered model appears in the host model API.
5. A runtime request reaches the mock server with the correct model ID.
6. Refresh, cache, credential, and service-restart behavior work as documented.

The tested OpenCode and `@opencode/plugin` versions must be recorded in the
release notes or integration test output.

### Security tests

Add assertions that representative credentials do not occur in:

- status reports;
- RPC responses;
- raw cache records;
- logs;
- diagnostics;
- serialized provider inventories; or
- generated documentation examples.

## Release gates

`v2.0.0` must not be published until all applicable gates pass:

- [ ] No V2 public operation reports success without performing the operation.
- [ ] V2 stable documentation and V1 legacy policy are consistent across the
      repository.
- [ ] V1 test suite passes without changing existing supported behavior.
- [ ] V2 unit, contract, integration, and security tests pass.
- [ ] Compiled entrypoints load in the supported host modes.
- [ ] npm tarball contents have been inspected.
- [ ] Upgrade from `v1.10.0` has been tested.
- [ ] A release candidate has been exercised with at least one custom
      OpenAI-compatible provider.
- [ ] Release notes identify supported host versions and deferred features.

## Suggested implementation order

1. Decide the V2 override policy and remove the current false-success stubs.
2. Add V2 lifecycle, credential, cache, and runtime integration tests.
3. Fix implementation gaps exposed by those tests.
4. Freeze the V2 configuration, model projection, RPC, and security contracts.
5. Isolate and label the V1 adapter as legacy while preserving its tests.
6. Update README, configuration, migration, auth, upgrading, and release
   documentation.
7. Publish a release candidate and validate upgrade behavior.
8. Publish `v2.0.0` only after every release gate passes.

## Definition of done

The implementation is ready for `v2.0.0` when OpenCode v2 can be used as the
stable default for generic model discovery, credential management, runtime
execution, refresh, cache operations, TUI, and Agent Tools; OpenCode v1 still
works through the combined legacy adapter; and the published package and
documentation accurately describe both support levels.
